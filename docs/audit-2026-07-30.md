# Security & Legal Audit — multiplayer_ai

**Repository:** `/Users/franciscosoltero/Desktop/Code/multiplayer_ai`
**Branch audited:** `feature/the-record`
**Date:** 2026-07-30
**Method:** Scout inventory → adaptive specialist finders → 3-skeptic majority-vote verification panel per finding (lenses: reproduce, exploitability, missing-context). Findings below are only those that survived the panel; refuted candidates are preserved in the appendix for review transparency.

---

## 1. Executive summary

The codebase is in materially better shape than a typical proof-of-concept: subprocess calls uniformly use `execFile`/`execFileSync` with argv arrays (no shell injection anywhere), all SQL goes through `better-sqlite3` prepared statements with positional bindings (no SQLi vector found), the standalone server's GitHub OAuth path is fail-closed at boot and re-checks the allowlist on every privileged message, and no live credentials exist in tracked files. **Zero critical and zero high-severity findings survived verification.** The residual risk is concentrated in two places: the `poc/hub` component, which ships with no authentication and no TLS enforcement behind only a console warning and a loopback default; and a set of defense-in-depth gaps in `poc/server` where a protection the team already implemented in one place was not applied consistently in another — the missing `maxPayload` on the WebSocket listener (the hub sets it, the server does not), the unsanitized `intent`/tool-target fields in the cross-session LLM digest (the same module sanitizes `driverName` for exactly this reason), and the purely lexical worktree containment check that a symlink can redirect. The top three risks to address before any non-loopback deployment are: **(1)** the hub's absent auth/TLS enforcement, **(2)** the unbounded 100 MiB pre-auth WebSocket frame on `poc/server`, and **(3)** the cross-session prompt-injection path through unsanitized teammate-digest fields. On the legal side there is no copyleft contamination and no live compliance exposure, but the repo has no LICENSE and no `license` field in any manifest — a decision that must be made explicitly before any public release or npm publish.

#### M1. Unrestricted plugin-import URL enables server-side request forgery via `git clone`

| | |
|---|---|
| **File:line** | `poc/server/src/pluginStore.ts:22-26, 72-84`; call site `poc/server/src/server.ts:1544-1560` |
| **Category** | SSRF / server-side request forgery |
| **Panel** | 3 STANDS / 1 REFUTED |

**Evidence**

```ts
// pluginStore.ts:22-26
const gitClone: CloneFn = async (url, dest) => {
  await execFileAsync("git", ["clone", "--depth", "1", "--", url, dest], {
    timeout: 120_000,
  });
};

// pluginStore.ts:72-75 — the ONLY validation
async add(projectId: string, url: string, addedBy: string): Promise<AddResult> {
  if (!this.root) return { ok: false, error: OFF_ERROR };
  if (!url.startsWith("https://"))
    return { ok: false, error: "plugin url must be https://" };

// pluginStore.ts:84 — raw git error text returned to caller
return { ok: false, error: `clone failed: ${msg}` };
```

The `add_plugin` websocket handler has no driver/privilege gate — the code comment states: *"Anyone in the project may register a plugin (spec §1) — no driver gate. Accountability is the attributed plugin_change on the wire."* A repo-wide grep found zero DNS-resolution, loopback, link-local, or RFC1918 blocking logic anywhere in `poc/server/src`.

**Impact.** Any authenticated project member can direct the server process to open an outbound HTTPS connection (git smart-HTTP) to any host reachable from the deployment — internal services, other laptops' hub instances, cloud-metadata-style endpoints. The differentiated error text returned to the requester (DNS failure vs connection-refused vs HTTP status vs 120 s timeout) makes this a usable internal-network reconnaissance oracle. Argv-array `execFile` rules out shell injection, so this is request forgery and recon, not RCE. `--depth 1` bounds history size but not single-blob size, giving a secondary disk-exhaustion vector against `AGENT_PLUGINS_ROOT`. The feature is gated behind the operator setting `AGENT_PLUGINS_ROOT` (off by default), which reduces likelihood but not the vulnerability once enabled — and enabling it is its intended use.

**Remediation.** Restrict plugin-import URLs to an operator-configured host allowlist (e.g. `github.com` plus an internal git host via env var). Resolve the hostname and reject loopback, link-local (169.254.0.0/16), and RFC1918 targets before invoking `git`. Cap or redact the error text returned to the client so git's raw network output cannot be used as a probing oracle; log the full detail server-side only.

**Dissent (1 of 4).** One panelist refuted on missing-context grounds: `docs/superpowers/specs/2026-07-25-v6c-plugins-design.md` §1 and §8 name this exact risk category as a deliberate trusted-team PoC stance, and the same feature already accepts a strictly larger accepted risk (cloned plugins can carry hooks = shell execution, explicitly un-sandboxed this cycle). The majority held that documented acceptance does not remove the vulnerability, and that the narrow SSRF fix is still worth doing independently of the hook question. **This finding is duplicated by a second finder — see M6, which the panel evaluated separately and also carried 3–1.**

#### M2. Cross-session `<teammates>` digest interpolates unsanitized agent intent and tool-call targets

| | |
|---|---|
| **File:line** | `poc/server/src/digest.ts:100-125` (interpolation), `:81-84` (target extraction); source at `poc/server/src/agentDriver.ts:333`, `:817-825`; consumed at `agentDriver.ts:511`, wired at `poc/server/src/server.ts:1281-1293` |
| **Category** | Template injection (LLM prompt injection) |
| **Panel** | 3 STANDS / 0 REFUTED (unanimous) |

**Evidence**

`buildTeammateDigest` builds the `<teammates>` block with no character filtering on `o.intent` or `c.target`:

```ts
// digest.ts:106
- session "${o.id}"${status}: ${o.intent ?? "no declared intent yet"}
// digest.ts:109-112
recent activity: ${o.recentToolCalls.map(c => `${c.toolName}(${c.target})`).join(", ")}
```

The same module explicitly filters one neighbouring field, and says why:

```ts
// digest.ts:53-54
const driverName = o.driverName?.replace(CONTROL_CHARS, "");
// digest.ts:47-52 (comment)
// The driver NAME is the exception, which is why it alone is filtered on the
// way in... A newline therefore reaches this line intact, and one is all it
// takes to forge a second `<teammates>` entry in the agent's prompt.
```

`intent` originates from the agent's own `set_intent` MCP tool (`agentDriver.ts:168`, schema `{ text: z.string() }` — no character class) and is stored length-capped only: `this.session.append({ type: "intent_update", text: text.slice(0, 200) })` (`agentDriver.ts:333`). `recentToolCalls[].target` is the raw `input.file_path ?? input.pattern ?? input.path` from the SDK tool-use block, appended verbatim with no cap at all (`agentDriver.ts:822`), before any permission gate resolves. The digest is spliced into another session's prompt with plain concatenation at `agentDriver.ts:511`.

**Impact.** A newline plus `</teammates>` (or a fabricated `- session "..."` line) inside an intent or a tool-call path forges entries in the structured status block that *other* sessions' prompts treat as authoritative teammate state — the system prompt at `agentDriver.ts:204` explicitly instructs the agent to take it into account. Because both fields are LLM-generated and can themselves be steered by adversarial content the agent reads (a malicious repo file, a fetched web page), this is a two-hop path from untrusted external content into an uninvolved teammate's prompt. The upstream `relayProtocol` bounding that justifies the `driverName`-only exception covers wire-sourced fields (`id`, `contested`) — it does not cover `intent` or tool-call `target`, which are local-session values that never traverse the relay validators. No test or spec ruling covers this case; the adjacent `driverName` mitigation makes the omission look like an oversight rather than a decision.

**Remediation.** Apply the existing `CONTROL_CHARS` filter (plus a check for the literal `</teammates>`) to `o.intent` and every `recentToolCalls[].target` before interpolation, and to `latest.text` before it is wrapped in the `<oversight>` block at `server.ts:1289`. Longer term, JSON-encode peer status or fence each field independently so no data field can contain its own block delimiter.

#### M3. Worktree write-containment is purely lexical — a symlink redirects auto-approved writes outside the sandbox

| | |
|---|---|
| **File:line** | `poc/server/src/permissions.ts:82-95` (check), `:262-281` (sole auto-approve gate) |
| **Category** | authz / sandbox containment |
| **Panel** | 3 STANDS / 0 REFUTED (unanimous) |

**Evidence**

```ts
// permissions.ts:82-95
function isContainedWrite(workdir, input) {
  ...
  const workdirResolved = path.resolve(workdir);
  const resolved = path.resolve(workdir, filePath);
  return resolved === workdirResolved || resolved.startsWith(workdirResolved + path.sep);
}

// permissions.ts:262-281 — the only gate that skips the human round-trip
if (isContainedWrite(hooks.workdir, input) && contestedWriteReason(...) === null) {
  return { behavior: "allow" };
}
```

`path.resolve` is lexical string manipulation; `grep -rn "realpath\|lstat\|symlink" poc/server/src` returns **zero** matches. The module's own docstring (`permissions.ts:44-53`) records a prior live incident of a `Write` reaching outside the worktree with no approval — the incident this check was added to fix. `buildCanUseTool` is wired live into the SDK query at `agentDriver.ts:222`; there is no OS-level sandbox (no `sandbox-exec`, chroot, or container) anywhere in `poc/server/src`, so this check *is* the filesystem security boundary.

**Impact.** Any symlink inside the worktree pointing outside it converts every subsequent `Write`/`Edit`/`NotebookEdit` under that path into a silently auto-approved write landing outside the sandbox. Two realistic paths to plant one: (a) a human approves one ordinary-looking Bash command (`ln -s /Users/operator/.ssh .mpai/worktrees/x/link`) — `ln` is not on the auto-approve list, so this costs one approval and unlocks N silent writes; (b) more directly, `workspace.ts` provisions real `git worktree` checkouts from a shared branch, and git materializes committed symlinks (mode 120000) on checkout — a symlink committed by any teammate with push access appears in the worktree with **zero** approvals, entirely outside the Bash gate.

**Remediation.** Resolve the target with `fs.realpathSync`, falling back to the realpath of the nearest existing parent directory for not-yet-created files (the reason the lexical approach was chosen, per `permissions.test.ts:300-306`), and re-check containment against the resolved worktree root. Deny — i.e. fall through to human approval — on any symlink component resolving outside the worktree.

#### M4. Hub ships with no authentication and no TLS; enforcement is an operator warning only

| | |
|---|---|
| **File:line** | `poc/hub/src/main.ts:5-7, 27`; `poc/hub/src/hub.ts:374-377, 761-778, 992` |
| **Category** | crypto-config / access control |
| **Panel** | 3 STANDS / 1 REFUTED |

**Evidence**

```ts
// main.ts:5-7
// Loopback by default, like the server (A1a): the deployed port is reachable
// only through the reverse proxy. Set HOST=0.0.0.0 for LAN access.
const host = process.env.HOST ?? "127.0.0.1";

// main.ts:27 — the entire enforcement mechanism
console.log("auth OFF — v7b1 development hub, do NOT expose this to the internet");
```

`hub.ts` join handler: *"v7b1 runs with auth OFF and takes the browser's word, exactly as a standalone server does with auth off... Until then this hub must not be exposed to the internet."* `channel.identity` is taken verbatim from client-supplied `msg.userId`/`msg.name` with only `typeof` and length-slice checks. `httpServer` is plain `node:http` (no TLS), and `httpServer.listen(opts.port, opts.host)` passes `host` through with zero validation.

**Impact.** The critical contrast is with `poc/server/src/config.ts`, whose `validateProductionConfig` refuses to boot without `GITHUB_CLIENT_ID`/`SECRET`/`SESSION_SECRET`/`ALLOWLIST` once `CLIENT_DIST` is set. `poc/hub/src/main.ts` has no equivalent check at all: it passes `staticDir: process.env.CLIENT_DIST` straight into `startHub` with no validation, so the exact production-like combination (`CLIENT_DIST` set + `HOST=0.0.0.0`) is unguarded on the hub while it fails closed on the server. Once bound non-loopback, any WebSocket peer can send `join`/`identify` with an arbitrary `userId`, join any project, and read/write session events under a spoofed identity. `docs/tech-debt.md` independently records this as still-open (no origin check, no rate limiting, unvalidated userId). Note also that `deploy/RUNBOOK.md` and `deploy/Caddyfile` cover only `poc/server` — there is no runbook, reverse-proxy config, or service file for the hub, so no external process control fills the gap.

**Remediation.** Have the hub refuse to start when `HOST` is non-loopback and no auth/TLS signal is configured, mirroring `config.ts`'s fail-closed production validation — escalate beyond `console.log`. Track against the v7b2 auth work already referenced in the hub comments and planned in `docs/superpowers/plans/2026-07-27-v7b2-trust-and-pairing.md` before any non-dev deployment.

**Dissent (1 of 4).** One panelist refuted on missing-context grounds: the v7b1 plan explicitly scopes auth out ("v7b1's hub is a localhost/trusted-network development target"), `docs/tech-debt.md` names a hard pre-deployment security gate, and the v7b2 remediation plan is already fully drafted — so the "operator warning only" framing understates the layered process controls. The majority held that the code-level asymmetry with `poc/server` (which *does* fail closed) is a real, cheap fix worth logging regardless of documentation.

#### M5. `WebSocketServer` has no `maxPayload` — inherits `ws`'s 100 MiB default, unlike the hub's identical listener

| | |
|---|---|
| **File:line** | `poc/server/src/server.ts:799` (was cited as 784; drifted +15 by a later refactor), parse at `server.ts:1701` |
| **Category** | denial of service / framework misconfiguration |
| **Panel** | 3 STANDS / 0 REFUTED (unanimous) |

**Evidence**

```ts
// server.ts:799 — no maxPayload option
const wss = new WebSocketServer({ server: httpServer });
// poc/server/node_modules/ws/lib/websocket-server.js:74
maxPayload: 100 * 1024 * 1024
// server.ts:1701 — runs on every frame, before any auth gate
msg = JSON.parse(raw.toString());
```

`denyUnauthed()` is checked inside `handleMessage`, i.e. strictly *after* `JSON.parse` has already run, and by the code's own comments `identify` and `peek_invite` are never gated by it at all. The sibling hub sets exactly this option with exactly this rationale:

```ts
// poc/hub/src/hub.ts:405-411
// maxPayload is applied here, before any gate, because the upgrade completes
// before authentication — a limit that only protects authenticated peers
// protects nothing (spec §10.2). `ws` otherwise defaults to 100MB.
const wss = new WebSocketServer({ server: httpServer, maxPayload: MAX_FRAME_BYTES });
```

The outbound relay client in the same package also sets it (`relay.ts:427`, `MAX_FRAME_BYTES = 1_000_000` in `relayProtocol.ts:23`). No per-connection or per-IP connection/rate limit exists in `server.ts` to bound the multiplier.

**Impact.** Any client that can complete the WebSocket handshake — no cookie required to open the socket or send the first frame — can send up to 100 MiB in a single frame, repeated across many connections, forcing the process to buffer and synchronously `JSON.parse` each one, blocking the event loop and inflating memory until every session on the box goes down. This is not hypothetical in the project's own topology: `deploy/Caddyfile` and `deploy/RUNBOOK.md` describe a public-domain TLS-terminating Caddy in front of the loopback port, explicitly noting *"reverse_proxy passes WebSocket upgrades through natively — no extra config"* — i.e. no proxy-side frame cap either. `MAX_PROMPT_LENGTH` (4000) only bounds `msg.text` after parse and does not prevent the cost. This is a consistency gap, not a design choice — the fix pattern is implemented one package over.

**Remediation.** Set `maxPayload` on the `WebSocketServer` at `server.ts:799` — reuse `MAX_FRAME_BYTES` from `relayProtocol.ts`, or a bound sized to `MAX_PROMPT_LENGTH` plus protocol overhead — matching the pattern and rationale already documented in `hub.ts:405-411`.

#### L1. Invite seat/`maxUses` enforcement is keyed on client-supplied `userId` when auth is disabled

| | |
|---|---|
| **File:line** | `poc/server/src/invites.ts:98-113, 160-166`; `poc/server/src/server.ts:1032-1044` |
| **Category** | authz |
| **Panel** | 3 STANDS / 1 REFUTED |

**Evidence.** `redeem()` tracks seats via `invite.redeemedBy.add(userId)` (a `Set<string>`), and `classify()` enforces capacity purely by `invite.redeemedBy.size >= invite.maxUses`. The join handler only overwrites the claimed identity when auth is configured:

```ts
const joinAuth = requireAuth(io.cookieHeader, opts.auth);
if (!joinAuth.ok) return sendError(joinAuth.error);
if (joinAuth.login !== null) { msg.userId = joinAuth.login; msg.name = joinAuth.login; }
```

`auth.ts:172`: `if (!cfg) return { ok: true, login: null };` — with auth off, the overwrite never fires and `msg.userId` is whatever the client sent (type-checked only). `main.ts:59-60` logs *"GitHub auth OFF — anonymous identities (development)"*, and `REQUIRE_INVITE`/`INVITE_MAX_USES` are independent env knobs usable in that mode. The invite store is the only capacity control in the server.

**Impact.** In auth-off deployments, a single actor can mint a fresh `userId` per reconnect and consume unlimited invite seats, defeating `maxUses` as a capacity or access control. Blast radius is bounded to session admission.

**Remediation.** Either document explicitly that invite seat limits provide no access control when auth is off, or bind seat consumption to a server-observed value (per-connection fingerprint) rather than a client assertion in that mode.

**Dissent (1 of 4).** One panelist refuted: `config.ts`'s `validateProductionConfig` makes auth-off impossible in production (any run with `CLIENT_DIST` set requires all four auth vars or refuses to boot), and the behavior is already documented verbatim in `docs/superpowers/specs/2026-07-27-a2a-github-oauth-design.md` §2 and in `auth.ts`'s `requireAuth` docstring — so the finding's own remediation is already satisfied. The majority retained it at low severity as a documentation-completeness item.

#### L2. No session revocation — logout and allowlist removal do not invalidate issued cookies

| | |
|---|---|
| **File:line** | `poc/server/src/auth.ts:14-17, 45-70, 271-284` |
| **Category** | authz / session management |
| **Panel** | 3 STANDS / 0 REFUTED (unanimous) |

**Evidence.** `auth.ts:14-17`: *"Seven days... There is no revocation list (spec §7)."* `/auth/logout` only clears the cookie client-side (`"set-cookie": cookie(SESSION_COOKIE, "", 0, isSecure(req, cfg))`) with no server-side state mutation. `verifySession` validates purely by HMAC signature and `iat` age, consulting no store or denylist — confirmed by inspection of the whole module; `hmac` is keyed solely off a single shared `sessionSecret` with no per-session component.

**Impact.** An exfiltrated cookie (XSS elsewhere, shared machine, leaked log) remains valid for the full 7-day TTL regardless of the user logging out. Allowlist removal *is* effective — `requireAuth` re-runs `isAllowlisted` on every call (`auth.ts:175-177`) — so offboarding works; but a still-allowlisted user's stolen cookie cannot be revoked short of rotating `SESSION_SECRET`, which invalidates every session. `HttpOnly`/`SameSite`/`Secure` flags reduce theft likelihood but do not close the gap once a cookie leaks by any means.

**Remediation.** Accepted and documented for the PoC (spec §7). If the product moves toward production, add a minimal revocation mechanism — a denylist of `iat`/login pairs, or short-lived sessions plus refresh tokens — so incident response can invalidate one session without a global rotation.

#### L4. No application-level security headers — protection delegated entirely to the reverse proxy

| | |
|---|---|
| **File:line** | `poc/server/src/server.ts:~730-782`; `poc/hub/src/hub.ts:374-403`; contrast `deploy/Caddyfile:8-20` |
| **Category** | crypto-config / defense in depth |
| **Panel** | 3 STANDS / 1 REFUTED |

**Evidence.** The `createServer` handler (healthz, auth routes, static/SPA fallback) sets only content-type headers. `grep -n "X-Frame-Options|Content-Security-Policy|X-Content-Type-Options|helmet|Referrer-Policy"` across `poc/server/src` and `poc/hub/src` returns **zero** matches, and neither package depends on helmet or equivalent. The only place these headers exist in the repo is `deploy/Caddyfile:8-20` (HSTS, `X-Content-Type-Options`, `X-Frame-Options DENY`, `Referrer-Policy`) — whose own comment notes the approval UI is clickjacking-sensitive because *"this product's core interaction is a human clicking 'approve' on a privileged action."* There is no Caddyfile, RUNBOOK entry, or service file for the hub at all.

> **Correction to the original filing:** the clickjacking quote was attributed to `auth.ts` comments; it is actually a `deploy/Caddyfile` comment. The substance is unchanged (and arguably stronger — it is an explicit design note).

**Impact.** Anyone running `poc/server` or `poc/hub` directly — dev, or a deployment that misconfigures the documented Caddy front-end — serves the approval UI with no `X-Frame-Options`/CSP. Both components default-bind to `127.0.0.1`, which narrows but does not eliminate exposure: a malicious page can still iframe `http://localhost:PORT` from the victim's own browser (the classic localhost drive-by), and the code documents `HOST=0.0.0.0` as a supported LAN mode with no header guidance for the hub.

**Remediation.** Set baseline headers (`X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY` or a `frame-ancestors` CSP, `Referrer-Policy`) directly in the `server.ts`/`hub.ts` response paths so protection does not depend on correct proxy configuration, and add the same Caddyfile/RUNBOOK guidance for the hub that exists for the server.

**Dissent (1 of 4).** One panelist refuted: both components default to loopback (an actual code-level compensating control the finding under-weighted), and the hub's missing Caddyfile is explained by its explicitly-announced non-production status.

#### L5. Install-time script (`postinstall`) in transitive dependency `esbuild`

| | |
|---|---|
| **File:line** | `poc/server/node_modules/esbuild/package.json:9-11`; identical in `poc/hub/node_modules/esbuild/package.json` |
| **Category** | supply chain |
| **Panel** | 3 STANDS / 0 REFUTED (unanimous) |

**Evidence.** `"scripts": { "postinstall": "node install.js" }` in esbuild@0.28.1, reached transitively via `tsx` and `vitest`→`vite`. `install.js` (300 lines, read) only fetches the matching `@esbuild/<platform>` binary from `https://registry.npmjs.org` as a fallback when the optional dependency did not resolve. A recursive scan of all three workspaces' `node_modules/*/package.json` for `postinstall`/`preinstall`/`install` keys found **no other** packages with install-time scripts (`better-sqlite3@13.0.2` ships prebuilds and defines none). The lockfile pins esbuild 0.28.1 with a sha512 integrity hash and `"dev": true, "hasInstallScript": true`.

**Impact.** esbuild's postinstall is a long-standing, widely audited pattern and not a novel vector. It is recorded because any install-time script is a standing risk surface: a compromised release via maintainer account takeover would execute arbitrary code during `npm install` on CI and dev machines. Lockfile integrity protects `npm ci` at the pinned version but not a future intentional version bump. Dev-only scope bounds the blast radius to build/test environments.

**Remediation.** No action beyond standard hygiene: keep esbuild pinned via the lockfile (already the case), and consider `npm ci --ignore-scripts` in CI jobs that do not need the binary (type-check-only), falling back to plain `npm ci` for build/test jobs.

## 3. Refuted findings appendix

These candidates were raised by finders and **did not survive** the skeptic panel. They are preserved so reviewers can see what was checked and why it was dismissed — several are technically accurate observations whose severity framing or exploitability did not hold up.

### A.1 `baseRef` reaches `git` argv without the leading-dash guard used elsewhere
**File:** `poc/server/src/workspace.ts` (vs. the guard in `poc/server/src/touched.ts:105-109`) · **Vote:** 1 STANDS / 2 REFUTED
**Why refuted.** The asymmetry is real — `touched.ts` rejects `baseRef === "" || baseRef.startsWith("-")` and `workspace.ts::provision()` does not. But two panelists empirically tested the actual construction and found an effective compensating control. `workspace.ts:85` passes `` `${baseRef}^{commit}` `` (not raw `baseRef`) to `git rev-parse --verify --quiet`, and the appended literal suffix corrupts any dash-prefixed token so git cannot parse it as an option. Every payload tested (`-x`, `-q`, `--all`, `--upload-pack=…`, `-C/tmp`, `--work-tree=/tmp`, `--`) exited non-zero, and that failure is caught at `workspace.ts:86-88`, returning before the `git worktree add` call at line 101 is ever reached. Git also rejects ref names beginning with `-` outright via `check-ref-format`. The finder's own impact section hedged that this "would most likely just fail" — testing upgraded that to "always." Cosmetic/stylistic inconsistency, not a security gap.

### A.2 Relay/hub path bypasses the GitHub OAuth allowlist — identity spoofing and machine hijack
**File:** `poc/server/src/server.ts:833-841, 1024-1038`; `poc/hub/src/hub.ts:445-470, 757-775`; `poc/hub/src/main.ts:27` · **Severity claimed:** HIGH · **Vote:** 1 STANDS / 2 REFUTED
**Why refuted.** The mechanism is confirmed real: `denyUnauthed()` returns `false` unconditionally for `io.mode === "relay"`, the relay `join` branch stamps identity from `io.stampedIdentity` without `requireAuth`/`isAllowlisted`, the hub verifies nothing, and `hello` lets any client claim an arbitrary `uplinkId` (evicting the legitimate laptop). Refuted on **severity framing**, not facts. First, `poc/hub/src/main.ts:7` binds `127.0.0.1` by default — an enforced code-level guard, not the "operator discipline" the finding claimed — and no deployment artifact in the repo (`deploy/multiplayer-ai.service`, `env.example`, `Caddyfile`, `RUNBOOK.md`) deploys or exposes the hub at all. Second, this is a formally documented, gated pre-production milestone: PRD Decision D12 and §8.10 name it as an explicit exposure gate; `docs/tech-debt.md` opens with "the security section must be cleared before the hub is publicly reachable"; and `docs/superpowers/plans/2026-07-27-v7b2-trust-and-pairing.md` is a complete, task-level plan implementing exactly the finding's remediation. Reaching a "high severity, production-defeating bypass" requires an operator to override the loopback default against explicit repeated warnings. **The underlying gap is still real and is captured at appropriate severity as M4.**

### A.3 No Origin/Referer allowlist on the WebSocket upgrade (CSWSH defense in depth)
**File:** `poc/server/src/server.ts:1661-1673` · **Vote:** 1 STANDS / 2 REFUTED
**Why refuted.** Facts confirmed: no `verifyClient`, no Origin check anywhere, session auth relies on a `SameSite=Lax` cookie. But the session cookie is also `HttpOnly`, so page JS cannot read it or attach it to a hand-rolled handshake, and the browser WebSocket API cannot set custom headers. The only viable path is automatic cookie attachment on a cross-site WS handshake — which `SameSite=Lax` blocks in every currently-shipping mainstream browser, because a WS handshake initiated by page JS is a subresource request, not a top-level navigation. The finding itself conceded exploitation would require "a browser bug, extension, or older client" without naming one. Separately, `docs/tech-debt.md` §1.4 already tracks this verbatim ("No `Origin` check on the WebSocket upgrade... Recorded in v7 spec §10.6"), triaged "can ship" during the A2a review, and `deploy/RUNBOOK.md` is marked "Status: NEVER EXECUTED." Legitimate hardening recommendation; not a demonstrable vulnerability. *(Filed twice by different finders; both filings refuted 2–1 and 3–0 respectively. The second filing additionally miscited line numbers — `createConnection` is at 804, the connection handler at 1676.)*

### A.4 Transitive path-traversal advisory GHSA-frvp-7c67-39w9 in `@hono/node-server`
**File:** `poc/server/package-lock.json` · **Vote:** 1 STANDS / 2 REFUTED
**Why refuted.** The advisory is real and `npm audit` reproduces it (2 moderate, 0 high/critical, via `@modelcontextprotocol/sdk@1.29.0` → `@hono/node-server@1.19.15`). Refuted on two independent grounds. **Unreachable:** the vulnerable code is Hono's `serve-static` HTTP middleware; `grep -rn "modelcontextprotocol\|hono\|node-server" poc/server/src` returns zero hits, and the only MCP usage is `createSdkMcpServer` (`agentDriver.ts:162-234`), an in-process/in-memory server using `DirectConnectTransport` — no HTTP static-file transport is ever instantiated. **Wrong OS:** the bug is a Windows-specific encoded-backslash (`%5C`) path-parsing flaw; the deployment target is a Linux systemd unit behind Caddy on 127.0.0.1. Additionally, the finding's central remediation claim — that `npm audit fix` reports no safe path and the fix is blocked on upstream — was disproven: `npm audit fix --dry-run` proposes `@modelcontextprotocol/sdk 1.29.0 → 1.30.0` and `@hono/node-server 1.19.15 → 2.0.12`, both within the SDK's declared peer range. **Actionable takeaway despite refutation: run `npm audit fix` in `poc/server`; it resolves cleanly today.**

# Demo — v7b1, the hub relay spine (2026-07-28)

**What this shows:** a browser talking to the **hub** drives a session whose agent runs in a
**different process** — the laptop. The hub runs no agent and holds no API key. The laptop dials
**out** to the hub, so nothing needs an inbound port.

Roughly 5 minutes. Two browser tabs.

## Start it

```bash
./poc/demo-hub-relay.sh          # builds, starts both processes, creates a session
./poc/demo-hub-relay.sh stop     # when you're done
```

It prints two URLs. **Both are the hub** (`:4000`). The agent runs on the laptop (`:3001`).

| | |
|---|---|
| DRIVER tab | `http://127.0.0.1:4000/?session=hubdemo&name=alice` |
| SECOND tab | `http://127.0.0.1:4000/?session=hubdemo&name=ben` |

Logs: `poc/.demo-run/hub.log`, `poc/.demo-run/laptop.log`. The laptop's log should say
`attached to hub ws://127.0.0.1:4000/uplink`.

## The walk

### 1. The session appears, and streams

Open the **driver tab**. You should see `PARTY · 1`, `♠ alice 🛞 DRIVING · you`, and `● ONLINE`.

Type a prompt. The turn runs **on the laptop** and streams back to the hub: tool calls, tool
results, final text. Nothing about the browser tells you the work is happening in another process —
which is the point.

### 2. A second tab sees the same session

Open the **second tab**. `PARTY · 2`, alice still driving, `✦ ben · you`. The model picker and MODE
are disabled for ben — he's a watcher. There's a live `🛞 TAKE THE WHEEL` button.

Click it. `🛞 ben took the wheel` appears in **both** tabs and the wheel moves. That round trip went
browser → hub → laptop → back to both browsers.

### 3. The permission gate travels — this is the one that matters

As the driver, ask the agent to do something that needs approval:

> touch /tmp/hub-demo-proof.txt

**Use `touch`, not `echo`.** The SDK auto-approves trivially-safe bash *before* the driver gate is
consulted, so `echo` never gates. (The laptop log prints a `CLAUDE_SDK_CAN_USE_TOOL_SHADOWED`
warning at startup naming the tools this applies to — `Bash` is not one of them, but the SDK's own
safe-command list still short-circuits the trivial cases.)

A permission card appears. In the **non-driving** tab you'll see the card with `⏳ driver deciding…`
and **no buttons** — only the driver may answer. That's the product's existing rule, not a relay
limitation.

Take the wheel in the second tab, then click `[A]PPROVE` there. In the **first** tab:

```
🔐 PERMISSION CHECK   DECIDED
the agent wants to use Bash — not on the auto-approve list
touch /tmp/hub-demo-proof.txt
✅ approved by ben
```

And the file really exists on the laptop:

```bash
ls -l /tmp/hub-demo-proof.txt
```

Browser → hub → laptop → SDK → back, with the right person's name on the decision.

### 4. A laptop drop doesn't lose the session

In another terminal:

```bash
kill $(cat poc/.demo-run/laptop.pid)
```

The session goes `OFFLINE` in the browser but **stays listed** — the hub still holds its history.
Restart it:

```bash
(cd poc/demo-project && ~/.local/bin/mpai --port 3001 --hub ws://127.0.0.1:4000/uplink --no-open) \
  > poc/.demo-run/laptop.log 2>&1 &
```

**What you'll see is a known bound, not a bug you found:** the *old* session stays `OFFLINE`
forever. `mpai` mints a fresh random uplink identity on every launch, so the hub treats the
restarted laptop as a different machine. See §"Known bounds" in the v7b1 plan and
`docs/tech-debt.md` §2.3. A reconnect *within* one process — a network blip, or a hub restart —
resumes correctly and replays only the gap.

## Things you'll notice, all known and written down

- **A hub restart leaves the browser on a dead socket.** The client has no WebSocket reconnect at
  all, so the tab keeps showing live-looking buttons until you reload. Pre-existing, and equally
  true of the standalone server. (`docs/tech-debt.md` §4)
- **JOIN on an offline session opens empty.** The hub refuses the join before replaying the history
  it is holding. (`docs/tech-debt.md` §2.4)
- **NEW SESSION is disabled through the hub.** The hub sends `repo: null`, which gates the create
  form to "launch via the CLI (mpai) to create sessions". Create with `mpai new` instead.
- **Invite links don't work through the hub** — `peek_invite` has nowhere to route, so the landing
  page says `INVITE UNAVAILABLE`. (`docs/tech-debt.md` §2.5)
- **The plugins list reads empty on the hub.** Per-laptop plugin rosters land in v7b3. Laptop-local
  *skills* do come through — they're session facts, not the `plugins` array.

## Do not expose this

v7b1's hub runs with **auth off** and stamps a client-asserted identity — anyone who can reach the
port is whoever they say they are. It prints this at startup. v7b2 is the plan that adds GitHub
OAuth, device pairing, `Origin` checks and rate limiting, and nothing should be exposed before it
lands.
